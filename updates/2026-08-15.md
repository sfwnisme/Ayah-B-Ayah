# Update — 2026-08-15

Reading-experience release: a new Quranic typeface, an adjustable ayah font
size, and a full keyboard layer with an in-app shortcuts dialog. Written for the
next developer or agent: what changed, why it is shaped this way, and the traps
that are not obvious from the diff. Start from `updates/2026-07-11.md` for the
original architecture — none of it was restructured here.

## Change history (chronological)

1. **Typeface swap** — the ayah face is now **KFGQPC Uthman Taha Naskh v2.0**
   from the [King Fahd Glorious Quran Printing Complex](https://fonts.qurancomplex.gov.sa/nashkh-font/),
   replacing Amiri Quran as the display font. Amiri stays bundled as a
   per-character fallback (see the trap below).
2. **Font-size stepper** — **أ+ / أ−** buttons in the header, 16–44 px in 2 px
   steps, with the current value shown live between them. Persisted in
   `chrome.storage.local` under a new `fontSize` key.
3. **Keyboard layer** — arrows bound to *direction of travel*, `Space` as a
   combined scroll/advance key, `↑`/`↓` to scroll a long ayah, `+`/`-` to resize,
   `؟` to open help.
4. **Shortcuts dialog** — a **؟** button in the header opens a modal listing
   every binding.
5. **Docs + store assets refreshed** to match all of the above, and the store
   screenshots became reproducible: five 1280×800 scenes generated by
   `scripts/make-screenshots.mjs` instead of hand-shot pairs.

## What changed, and why it is shaped this way

### Font: why two faces are bundled

`UthmanTN_v2-0.ttf` is a general-purpose Naskh face, **not** the Quranic-mark
variant. It has 642 glyphs / 295 mapped code points, and it is missing:

- `U+0671` alef wasla (ٱ) — 13,483 occurrences in `data/`
- `U+06D6`–`U+06ED`, the waqf and small-high marks — ~18,000 more

**92.5% of the 6,236 ayahs contain at least one code point it cannot render.**
Shipping it alone would have put tofu boxes through nearly the whole Quran. So
the stack in `css/popup.css` is:

```
"KFGQPC Uthman Taha Naskh", "Amiri Quran", "Scheherazade New", …
```

Browsers fall back **per character**, so Uthman Taha paints the letters and
Amiri fills only the missing marks. Verified with CDP
`CSS.getPlatformFontsForNode` on the worst-case ayahs (2:196, 2:177, 4:12):
Uthman Taha ≈ 140 glyphs each, Amiri 10–17, no visible seam.

> If you ever obtain **KFGQPC Uthmanic Script HAFS** (the Quranic sibling, full
> mark coverage), it can replace both and the Amiri files can be deleted. That
> is the only clean way to get to a single-font build.

The TTF is a build input, converted by `scripts/convert-font.py` (fontTools +
brotli) into `fonts/uthman-taha-naskh.woff2` (139 KB → 57 KB).
`scripts/package.mjs` excludes `fonts/*.ttf` from the zip, so the source never
ships. `scripts/fetch-font.mjs` is still there — it re-downloads the Amiri
fallback subsets, which are still in use.

### Font size: one custom property, one clamp

`body` carries `--ayah-font-size`; `.ayah-text` is the only consumer, and
`.ayah-marker` is `0.67em` so the ﴿١٣﴾ marker keeps its ratio at every size
(it used to be a hardcoded 16 px).

`js/storage.js` owns `MIN`/`MAX`/`STEP` and `clampFontSize`, and both the getter
and the setter clamp. That is deliberate: a value hand-edited in devtools, or
written by a future build with different bounds, can never make the ayah
unreadable. There is a test for exactly this (`fontSize = "999"` → 44).

`applyFontSize()` is kept out of `render()`. Resizing must not re-fetch the
surah or rebuild the verse picker — `render()` does both.

### Keyboard: direction of travel, not next/previous

The arrows are bound to where things move on screen, matching the original
requirement that *previous* sits on the right and *next* on the left:

| Key | Action |
|---|---|
| `←` | next ayah (leftward = forward in RTL) |
| `→` | previous ayah |
| `Space` | scroll a long ayah one page, then advance at its end |
| `↑` / `↓` | scroll one line |
| `+` / `-` | resize the ayah |
| `Esc` | close the open dialog |
| `؟` / `?` | open the shortcuts dialog |

`Space` is the interesting one. `ayahCardIsAtEnd()` decides between scrolling
and navigating, with a **2 px tolerance** — Chrome reports fractional
`scrollHeight` at some font sizes, and without the tolerance the final press
would nudge the scroll instead of advancing. The page step is
`clientHeight - fontSize * 2`, i.e. one line of overlap, so no line is skipped,
and it scales with the chosen size rather than being a fixed pixel guess.

Two guards worth keeping:

- **`e.target.tagName !== "BUTTON"` on Space.** Without it, tabbing to **أ+**
  and pressing Space would both press the button and advance the ayah.
- **`modalIsOpen()` on everything.** The pickers run their own capturing
  handler; the help dialog does not. Without the guard, Space would page the
  ayah behind an open modal.

`render()` resets the card with `scrollTo({ top: 0, behavior: "instant" })` —
`"instant"` matters, because it must cancel the smooth scroll that may still be
animating from the keypress that triggered the navigation.

### Help dialog

Static markup in `popup.html`, not built in JS like the pickers, so the key list
lives in one readable, translatable place. It deliberately uses its own
`.help-overlay` class rather than `.picker-overlay`: the picker-leak regression
test counts `.picker-overlay` elements, and the help dialog is not a picker.

## Testing

`test/e2e.mjs` is now **54 checks** (was 20 — the file header had claimed 21,
which was wrong before this release; it is accurate now). New coverage: stepper
in both directions, both clamps, marker scaling, persistence across reload, a
corrupt stored size, every key binding, Space paging vs. advancing, scroll
reset, and the help dialog.

The Space test presses until the ayah changes and asserts it took **more than
two presses** on 2:282. Asserting only "it eventually advanced" would pass even
if paging broke entirely and the first press navigated.

Run it exactly as the file header says — **a fresh `--user-data-dir` each time**.
The "initial ayah" check expects no saved position, so a reused profile fails it
and the failure looks unrelated to whatever you were changing.

## Store assets

The screenshots are now **generated, not hand-shot**: `scripts/make-screenshots.mjs`
starts its own static server and headless Chrome, drives `store/stage.html` once
per scene, and writes five 1280×800 PNGs. The old pair had gone stale (Amiri
text, a header with no controls) precisely because they were made ad hoc, so the
script exists to keep that from happening again — re-run it after any UI change.

The stage renders the **live popup in an iframe**, so a shot cannot drift from
the shipped UI. Scene copy lives in `store/stage.html` (`SCENES`); the matching
popup state — position, font size, which modal to open — lives in the script's
own `SCENES`. The five cover reading, the picker + search, the font-size
stepper, the shortcuts dialog, and the offline/privacy pitch.

Two layout traps, both fixed in the stage:

- The popup body is a fixed 420×420. Sizing the iframe to the 546 px frame just
  anchors the body to the RTL start edge and leaves a gap; it needs
  `transform: scale(1.3); transform-origin: top right` instead.
- The pitch column was 430 px wide with a 54 px headline, which wrapped the
  Arabic headlines badly. 484 px / 44 px with `text-wrap: balance` holds them on
  one line.

**Choosing the search query matters.** The picker shot needs a query that
actually returns rows. `الذين امنوا` returns **zero** — the Uthmani text spells
it `ءَامَنُوا۟`, and `js/arabic.js` strips alef forms but not the standalone
hamza, so the bare-typed form never matches. That is the known recall gap in
"Future work", now with a concrete reproduction. The shot uses
`على كل شيء قدير` (6 hits in al-Baqarah).

`store/LISTING.md` documents the upload order; `store/PRIVACY.md` and the
listing's permission justification were updated because `chrome.storage.local`
now holds a second value, the font size.
